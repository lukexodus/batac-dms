Batac DMSArchitecture pattern — 07 / 30
Architectural pattern

Modular monolith

One Fastify process, not microservices — a deliberate choice, not a default.

Rationale, from the project's own ADR: a five-person team with minimal distributed-systems expertise, on-premise, expected to run 10+ years. Microservices trade simplicity for operational overhead this team doesn't have capacity for.

Isolation is enforced at the code and data level, not the network level — schema-per-module ownership, and an event bus as the only sanctioned cross-module channel.

Coupling is checked with dedicated coupling tests — a modular monolith only stays modular if something enforces the boundaries.

Batac DMSInfrastructure — 08 / 30
Cross-cutting concepts

Infrastructure primitives

Event bus

How modules communicate without direct dependency. A module emits an event, others subscribe — no module calls another module's code directly.

Drizzle-per-schema

Each module owns its own database schema. Data access goes through Drizzle repositories scoped to that schema.

pgboss for durable jobs

Background work — timers, SLA evaluation, retries — runs through pgboss, not in-process timers, so jobs survive a server restart.

Batac DMSDirectory Structure — 11 / 30
Project Organization

Directory Structure & Inter-dependency

├── apps/ │ ├── portal/ # Public facing Next.js app (Pending) │ ├── server/ # Fastify Modular Monolith Backend │ └── web/ # Internal Staff React SPA (Vite) ├── packages/ │ ├── config/ # Shared TS/ESLint configs │ ├── database/# Drizzle schemas & migrations │ ├── shared/ # Zod schemas, errors, domain events │ └── ui/ # Shared React Component Library ├── docs/ # Architecture & Specs (Source of Truth) └── tools/ # DevOps scripts, DB init

Strict Dependency Flow: apps/ can depend on packages/, but packages cannot depend on apps. Packages cannot circularly depend on each other.

packages/database: Centralizes the Drizzle schema and migrations. Used extensively by apps/server. Schema is divided per-module reflecting the modular monolith architecture.

packages/shared: The "glue" contract. Contains Zod schemas (API boundaries), domain events (cross-module communication), and custom errors. Used by both frontend and backend to ensure end-to-end type safety.

docs/: Not just a folder. Architecture documents here act as the highest source of truth for the system.

Batac DMSModule: IAM — 15 / 30
Module deep dive

IAM — auth architecture Done

Identity and access management — authentication and authorization for all users of the system.

Two-layer security model: Attribute-Based Access Control (ABAC) at the application logic layer, PostgreSQL Row-Level Security (RLS) as a database-enforced backstop.

Access control isn't just "trust the application code" — even if application logic has a bug, the database itself refuses to return rows a user isn't authorized to see.

Batac DMSModule: IAM security model — 16 / 30
Module deep dive

IAM — security model

RLS policies, concretely: 4 CREATE POLICY statements across IAM and Documents schemas — session ownership/admin access, office-based document isolation, and a policy excluding the IT-admin role from confidential document content even though IT-admin has broad system access otherwise.

That last point is ABAC+RLS working together: an IT admin can manage the system without reading confidential document contents — enforced at the database level, not just an application-level check.

Batac DMSModule: AUDIT — 17 / 30
Module deep dive

AUDIT Done

Hash chain

Each audit entry cryptographically linked to the previous via createHash('sha256') and createHmac('sha256', secret) — Node's built-in crypto only, no external library. timingSafeEqual used wherever signature/hash comparison happens.

Grants, DB-enforced

A dedicated batac_audit role has UPDATE and DELETE explicitly revoked on audit tables — entries can be inserted, never modified or deleted, enforced by grants, not just app logic. An over-permissive grant was caught and fixed (resolved 2026-06-24).

Coverage & export

Real test coverage exists here — worth noting alongside Workflow's zero (slide 21). Exports in RFC 3161 timestamp-authority format for independent verification.

Claim boundary, stated precisely

Documented as "tamper-evident, not tamper-proof" — it provides evidence that tampering occurred, not prevention of tampering. Worth stating exactly this way rather than rounding up to "tamper-proof."

Batac DMSModule: ORG — 18 / 30
Module deep dive

ORG Done

Manages office hierarchy and delegation of authority — e.g. an office head delegating signing authority while away.

Delegation mechanism, precisely: grants are rows in a dedicated table, created when a Designation document is logged. One active designation per person is enforced via a database-level partial unique index — one of the project's named architectural invariants (Invariant #16).

The grant takes effect immediately on successful insert — no separate admin-confirmation step. Scope is time-bounded via an end-date field; "time-bounded scope" is the accurate description, not a named "auto-expiry" feature.

Optional, if there's time: one still-open, non-blocking design question — whether roles like "Acting Mayor" are literal seeded role assignments or need a different enforcement path based on delegation scope. Doesn't need resolving before current seed data, only before delegation grants for Mayor-equivalent authority go live.

Batac DMSModule: DOCS — 19 / 30
Module deep dive

DOCS Done

The core document lifecycle module — documents move through a defined state machine from submission to final disposition.

Two-stage numbering: a preliminary series number is assigned at intake; the full mechanism is covered next (Tracking), where it connects to QR assignment.

Files upload direct-to-S3 — not routed through the application server as a bottleneck — with an OCR pipeline for scanned documents.

Versioning is built in — revisions are tracked, not overwritten.

Batac DMSModule: TRACK — 20 / 30
Module deep dive

TRACK Done

Public-facing document tracking — anyone can scan a QR code to check a document's status, no login needed.

QR-before-numbering, precisely: per the project's ADR, the QR code — a UUID — is assigned first, during the Secretariat's initial logging transaction, before the preliminary series number. Once assigned, it's immutable and independent of whatever numbering happens afterward.

Routing history is append-only — every step a document takes through offices is recorded and never overwritten, giving a complete audit trail of where a document has been.

Page-blurring rule for public lookups: first page visible via a pre-rendered image, subsequent pages blurred. "Get a copy" leads into the formal Document Request Form flow, which requires Vice Mayor and SP Secretary approval — public visibility is intentionally limited, full access goes through a real approval gate.

Batac DMSDocumentation — 23 / 30
Engineering practices

Documentation-driven development

Runs on a substantial pre-development documentation set: architecture documents, Architecture Decision Records for major technical choices, and a routing file (AGENTS.md) directing contributors to the right document for a given question.

Findings and issues get logged in an append-only findings log as they're discovered — including the audit-grants over-permission issue caught and fixed (slide 16), documented rather than quietly patched.

A big part of why a small team maintains architectural discipline without a dedicated architecture team — decisions are written down once and referenced, not re-litigated per pull request.

Batac DMSDatabase discipline — 24 / 30
Engineering practices

Database & schema discipline

Schema-per-module — each module owns its own PostgreSQL schema, enforcing the modular monolith boundary at the data layer (slide 7).

No cross-schema foreign keys — modules can't create hard database-level dependencies on each other's internals, only through the event bus.

Migrations-only — schema changes go through versioned Drizzle migrations, not manual edits. 7 migrations exist to date, including Workflow's schema migration (schema exists even though application logic doesn't yet — schema-first).

All migration SQL is under version control, reviewable like any other code change.

Batac DMSRisks — 28 / 30
Honest accounting

Risks & open items

Development-time unknown vs. documentation gap

The project's own planning docs distinguish these explicitly. Several things genuinely cannot be pre-decided no matter how much documentation exists up front — and are listed as such, not as oversights.

Examples: exact Drizzle/PostgreSQL edge-case behavior for complex constraints; SSE reconnection behavior under intermittent connectivity (relevant for lower-connectivity Barangay contexts); pgboss retry/dead-letter behavior for long-running timers; OCR quality calibration.

All explicitly framed as legitimate decisions that can only be made once real implementation and real data exist — not gaps in planning.

Smaller open items: Phase 2 will need to enforce MFA more strictly — deferred by design for Phase 1, not forgotten. Known implementation gaps are actively tracked in the design documentation as found.
