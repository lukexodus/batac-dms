# ADR-GEN-013: Advisory Lock for Audit Chain-Hash Serialization

**Status:** Accepted **Date:** June 2026 **Deciders:** Development team (resolving TASK-AUDIT-004 / LOG-0011)

---

### Context

The audit log system requires that each audit event carries a cryptographic `chain_hash` computed from the previous event's hash and the current event's payload, forming an append-only tamper-evident log (Security Invariant #3; I3 §16). To ensure hash consistency and prevent race conditions when concurrent requests write audit events, event inserts and their chain-hash calculations must be strictly serialized.

The default pattern for serializing writes on a table is a row-level lock, generated by Drizzle's `.for('update')` (compiling to `SELECT ... FOR UPDATE` in PostgreSQL). However:
1. Under Security Invariant #3, the `batac_audit` database role explicitly revokes `UPDATE` and `DELETE` privileges on the `audit.events` table to ensure that even if the runtime application is compromised, historical audit records cannot be altered or removed.
2. In PostgreSQL, executing `SELECT ... FOR UPDATE` on a table requires the `UPDATE` privilege on that table, even if no actual update is performed.
3. Therefore, executing a row lock as the `batac_audit` role fails with a database permission error.

### Decision

We resolve this by standardizing on **transaction-level PostgreSQL advisory locks** (`pg_advisory_xact_lock`) to serialize concurrent chain-hash computations instead of row-level locks.

Advisory locks are application-defined locks that do not lock physical rows or tables. They are transaction-scoped (automatically released when the transaction commits or aborts) and do not require any table privileges (any database role has permission to call advisory lock functions by default).

1. **Lock Scoping:**
   - The transaction-level lock is acquired inside the audit transaction prior to reading the previous chain hash:
     ```sql
     SELECT pg_advisory_xact_lock(314159265); -- a constant key representing the audit event lock namespace
     ```
2. **Implementation in `AuditRepository`:**
   - Drizzle's `sql` helper is used to invoke `pg_advisory_xact_lock` before executing the SELECT query for the last chain hash.

### Alternatives Considered

* **Row-level lock (`SELECT ... FOR UPDATE`)**: Rejected because it requires granting `UPDATE` privilege to `batac_audit`, which directly violates Security Invariant #3's append-only design.
* **Table-level lock (`LOCK TABLE`)**: Rejected because locking the entire `audit.events` table for write/read is extremely heavy and degrades performance under concurrent load, and it also requires elevated table privileges.

### Consequences

**Positive**
* Strictly serializes concurrent audit chain-hash computations, guaranteeing cryptographic log integrity.
* Adheres fully to the principle of least privilege by keeping `batac_audit` as a strict `SELECT` and `INSERT` only role with no `UPDATE` privilege.
* Locks are automatically and safely released by PostgreSQL at transaction boundaries, avoiding connection deadlocks on process failures.

**Negative / Trade-offs**
* Advisory locks are cooperative. Any write query executed outside of this cooperative locking pattern will bypass the serialization, potentially causing race conditions. This is mitigated by channeling all audit writes strictly through the `AuditRepository` and confirming that no raw SQL inserts are executed elsewhere.
